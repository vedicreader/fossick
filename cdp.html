Driving Chrome from Python: page snapshots for agents, forms, step lists, network capture and cookies

Some web work cannot be done with downloads alone. A page may need a login, a click on a button, or a form filled in before it shows anything useful. This module drives a real Chrome through the Chrome DevTools Protocol (CDP), the interface Chrome’s own developer tools use, by way of fastcdp.

It uses one long-lived Chrome, separate from the one you browse with. It listens for remote control on port 9223 and keeps its own profile, by default in ~/.cache/fastcdp/cdp-chrome, so anything you log in to there stays logged in across restarts. cdp_connect attaches to that Chrome and starts it first if it is not running; cdp_setup only starts it. cdp_ws returns its websocket address, which scrapling’s browser fetchers accept as cdp_url, and cdp_app opens a URL in it as an app window with no tabs or address bar. debug_ready tells you whether that Chrome is up without starting it: it asks the DevTools endpoint for /json/version, because Chrome opens the port a moment before it can answer there.

The functions here are async, so call them with await, or wrap them in syncy from synchronous code as the examples do. Most of them are methods added to fastcdp’s CDP connection and Page classes. On a page, snapshot gives an agent a short text map of the controls it can use, fill_form and act operate those controls by their visible labels, calls records the network requests the page makes, and md returns the live page as markdown.

Managing the debug Chrome

Chrome’s DevTools endpoint can be inspected with plain HTTP. /json/version describes the browser and /json/list lists its open tabs. The first cell below lists them. The second closes a tab, quits the browser, and starts it again in a visible window with cdp_setup(headless=False), which is how you log in to a site by hand. The cookies are saved in the profile, so they survive later restarts.

# LIST — is a debug Chrome up, and what's open in it?
import httpx
port = 9223
print('running on 9223?', _debug_running(port))
ver = httpx.get(f'http://127.0.0.1:{port}/json/version').json()
print('browser:', ver['Browser'], '| ws:', ver['webSocketDebuggerUrl'])
for t in httpx.get(f'http://127.0.0.1:{port}/json/list').json():   # open tabs/pages
    print(' ', t['type'], '|', t['title'][:40], '|', t['url'][:50])
print('live debug ports:', [p for p in (9222, 9223, 9224) if _debug_running(p)])

App windows

cdp_app opens a URL in the debug Chrome as an app window, without tabs or an address bar, which suits a local web app. It reuses the running browser when there is one, so all its windows share the same profile and logins. It returns ok, the url, the port, the profile folder, reused (whether a browser was already running) and target, the id of the new window once Chrome reports it. The first test checks the launch flags without starting a browser and the second runs cdp_app against stand-ins for Chrome.

# cdp_app's flags: an app window, headed, on the persistent profile. No browser is launched here.
flags = _chrome_flags(9223, _profile_dir(), False, ['--app=http://alpha.localhost:5001/'])
assert '--app=http://alpha.localhost:5001/' in flags
assert '--headless=new' not in flags                  # an app window you cannot see is useless
assert f'--user-data-dir={_profile_dir()}' in flags   # same profile as cdp_setup, so logins carry
assert str(_profile_dir()).endswith('cdp-chrome')
assert _profile_dir('~/x') == Path.home()/'x'         # user_data_dir wins, and ~ is expanded
# cdp_app end to end against a stubbed browser: reuse a running Chrome, report its target.
# The stubs rebind this notebook's own names, because that is what `cdp_app` resolves at call
# time -- patching `fossick.cdp` would leave the definitions in these cells untouched.
import httpx, subprocess as _sp

_saved = (debug_ready, _sp.Popen, httpx.get)
launched = []
class _Targets:
    def json(self): return [{'id': 'target-1', 'url': 'http://alpha.localhost:5001/'}]
try:
    debug_ready = lambda port, host='127.0.0.1': True     # a debug Chrome is already up
    _sp.Popen = lambda args, **kw: launched.append(args)
    httpx.get = lambda url, **kw: _Targets()
    r = cdp_app('http://alpha.localhost:5001/', wait=1)
finally:
    debug_ready, _sp.Popen, httpx.get = _saved

assert r['ok'] and r['reused'] is True         # reused, so no second resident browser
assert r['target'] == 'target-1'               # and the window was found by its url
assert r['url'] == 'http://alpha.localhost:5001/' and r['port'] == 9223
assert '--app=http://alpha.localhost:5001/' in launched[0]
assert f'--user-data-dir={_profile_dir()}' in launched[0]
print('cdp_app:', {k: r[k] for k in ('reused', 'target')})
cdp_app: {'reused': True, 'target': 'target-1'}

b = cdp_app('https://example.org/')

Recording network requests

calls records the requests a page sends while it loads. Given a url, it opens that page in a new tab and listens until tail seconds after it loads. Without one it only listens, for twice tail seconds. It returns a dictionary keyed by request id, holding each request whose URL matches pattern and, where Chrome still has it, the response body under response_body. replay_xhr in fossick.core can then send any of them again without the browser.

cdp_cookies exports the debug Chrome’s cookies, optionally only those for one site. By default it returns them in the list format Playwright and scrapling accept as cookies=; with as_dict=True it returns {name: value}. fetch(url, session=True) uses it to send your logged-in cookies with a request.

Acting on a page

An agent needs to know what it can click or type into, and a full page of HTML is far too long to read for that. snapshot builds a short text view from the accessibility tree, the description of the page that screen readers use. Each control becomes one line, [#id] role "name", such as [#42] button "Add to cart", where the id is Chrome’s number for that element. With interactive=False it also lists headings, forms and other landmarks.

The other methods act on the page. type_text clears a field before typing, unlike fastcdp’s fill_text, which adds to what is already there. click_settle clicks and then waits for the page to settle, without failing when a click on a single-page app does not navigate. fill_form fills fields by their visible label or name, given as {label: value}, chooses options in drop-downs, optionally clicks a submit button by its name, and returns a fresh snapshot.

act runs a list of steps in order, which is useful when an agent has planned a whole flow. Each step is a tuple: ('goto', url), ('fill', label, value), ('click', label), ('select', label, value), ('wait', text), ('wait_sel', css) or ('read', css), which can take a label as a third item. It returns a dictionary with the markdown read by each read step, keyed by its label or selector. An unknown step raises ValueError.

Screenshots and annotation

collect gathers screenshots while a person browses. It adds a small bar with a capture button and a done button to the page. Each press of capture saves a screenshot, with the bar hidden. It stops when done is pressed, when count screenshots have been taken, or after tout seconds, and with every_n it also takes one every every_n seconds by itself. Screenshots are saved as PNG files in save_dir when one is given, and returned. BUTTON_JS, HIDE and SHOW are the scripts that draw, hide and show the bar.

annotate lets a person point at parts of a page. Each element they click is outlined and numbered, and when they press done it returns a screenshot with the numbers on it and a list with each element’s number, accessibility role, name and a CSS selector for it. An agent can use this to ask a person which button or field they mean. The scripts it injects are ANNOTATE_JS, ANNOTATE_BAR_JS and ANNOTATE_CLEANUP_JS.
